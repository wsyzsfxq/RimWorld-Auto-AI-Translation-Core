# 官方“泰南语”与缺译定位：静态分析

- 状态：已完成本地程序集静态分析；接入方案尚未实施。
- 日期：2026-11-04。
- 范围：本机 RimWorld 1.7 的 Keyed 查译文、伪翻译、官方缺译报告和 Def 字段枚举；对照 1.6 的对应入口。
- 依据：[当前设计基准](../designs/v4-five-stage-independent-translation-workflow.md)、[安全范围](../standards/security-scope.md)。本报告不修改已确认的翻译模式、数据保存方式或复用规则。
- 未进行：游戏方法调用、游戏界面操作、编译、测试、大模型请求、部署和推送。

**可以利用官方判断来更准确地找缺译，而且有比“监控变成泰南语”更完整的办法：原版已经提供了检查缺译目录的逻辑。**

建议结合两种信息：先按官方规则找出缺少译文的条目，再在实际查译文失败时补上使用位置。这样可以拿到原文和翻译键，不必从带重音的文字反推原文，也不必等每个设置页都打开一遍。

不过，这不等于能找全所有 Mod 的硬编码文字。直接把英文传给绘制函数、完全没有调用本地化接口的代码，仍需 DLL 分析或界面采集。

## 2. “泰南语”究竟何时出现

这里不是通过字体识别“这句话看起来像英文”。原版先查翻译键，查不到有效译文时，开发者模式才把默认语言文本换成带重音的样子。

本机 1.7 的 `Verse.Translator.Translate(string key)` 实际顺序是：

```text
按 key 查当前语言
  找到有效译文 → 返回译文
  没找到      → 按同一个 key 查默认语言原文
                  开发者模式开启 → 把原文变成“泰南语”
                  开发者模式关闭 → 原样显示默认语言文本
```

静态定位：该方法 `IL_0003` 调用 `TryTranslate`；失败分支 `IL_0014` 调用默认语言的 `TryGetTextFromKey`；`IL_001a` 检查 `Prefs.DevMode`；`IL_0027` 调用 `PseudoTranslated`。

`Translate(string, object[])` 也是先查原文模板、进行伪翻译，再调用 `String.Format` 填参数。例如先处理 `Stored {0} items`，然后填入数量；适合在填参数之前采集模板。

`LoadedLanguage.TryGetTextFromKey` 对以下情况返回失败：

- 没有这个键；
- 对应项目被标记为占位内容，例如加载器识别的 `TODO`；
- 键为 `null`。

空键、语言尚未准备好、默认语言里也不存在原文，不应自动变成待发给 AI 的自然语言条目。尤其是默认语言也找不到的键，可能只是拼错的标识。

`PseudoTranslated` 本身只是字符变换：替换字母，保留花括号包围的参数区域，并检查开发者模式。它没有原始翻译键、所属 Mod 或文件路径这些参数。

本次遍历 1.7 主程序集方法体，只有 `Translator.Translate` 的上述两个重载直接调用 `PseudoTranslated`。这说明它不是所有文本绘制的统一入口；不能把“没有出现泰南语”当作“已经正确翻译”。

## 3. 原版已经有全量缺译检查

### Keyed：不用打开页面，也可以列出缺译条目

`Verse.LanguageReportGenerator.AppendMissingKeyedTranslations` 的逻辑是：

1. 如果当前语言就是默认语言，直接结束。
2. 遍历默认语言中已经加载的全部 `keyedReplacements`。
3. 对每个键调用 `activeLanguage.HaveTextForKey(key, false)`。
4. 当前语言缺少有效项目时，列出键、默认语言原文、英文来源文件和行号。
5. 另外判断该键是否已有占位条目，并把占位来源写进报告。

这个检查不要求 `DevMode` 开启。`SaveTranslationReport` 的入口可能出现在开发工具中，但上述缺译判断本身没有开发者模式条件。

可借用其判断和结构化数据，不建议调用“保存报告”再解析一份面向人的文字报告。后者会产生不必要的文件操作，也更容易被报告格式变化影响。

默认语言的 `LoadedLanguage.KeyedReplacement` 还保存了：

- `key`、`value`；
- `fileSource`、`fileSourceLine`；
- `fileSourceFullPath`；
- `isPlaceholder`。

`LoadFromFile_Keyed` 明确将 `VirtualFile.FullPath` 写入 `fileSourceFullPath`。可优先按这个来源路径匹配已加载 Mod；不能只看哪个 DLL 调用了翻译，因为调用者可能是公共组件，原文却来自另一个 Mod。

### DefInjected：有单独的官方字段和缺译规则

`DefInjectionPackage.MissingInjections` 使用 `DefInjectionUtility.ForEachPossibleDefInjection` 遍历实际加载的 Def，并按归一化字段路径检查当前注入项目。

`ForEachPossibleDefInjection` 可接收 `ModMetaData`，按 `Def.modContentPack.PackageId` 筛选所属 Mod。其回调提供字段路径、字符串或列表内容、字段元数据和对应 Def；比从屏幕文字猜所属 Mod 更直接。

其中 `ShouldCheckMissingInjection` 还会区分：

- 自动生成的 Def；
- 空文本；
- `NoTranslate`、`Unsaved`、`MayTranslate` 等字段标记；
- `MustTranslate` 或需要特殊处理的 `SlateRef`；
- 其他未明确标记字段中的含空格文本。

这些属于原版缺译报告的具体规则，不等于所有自然语言的完美判断。我们已确认的 XML 宽召回规则仍有用途，不能直接用官方报告把原有候选整批删掉。

官方缺译目录中还包含加载错误、旧背景故事和多余注入等检查。它们可帮助诊断，不能全部混成新的 AI 翻译请求。

## 4. 哪些东西能找到，哪些找不到

| 内容 | 官方缺译目录 | 运行时查键失败 | 仍需其他办法的地方 |
|---|---|---|---|
| 已加载的 XML Keyed 原文，目标语言缺键或只有占位 | 能列出，包含未打开页面的键 | 实际查键时能记录 | 重复键来源应以实际加载结果核对 |
| Def 中需要本地化的字符串或列表 | 官方有单独枚举、缺译检查 | 通常不经过 `Translator.Translate(key)` | 保留 XML/Def 分析、字段原文和文件来源映射 |
| DLL 通过 `"SomeKey".Translate()` 取文字 | 键和英文已在默认语言目录时能列出 | 能记录准确 key 和模板 | 调用位置和原文所属 Mod 是两种不同信息 |
| Mod 先翻译，再把结果保存在静态字段中 | 能检查目录是否缺键 | 只在初始化或重新查键时触发 | 后续画面读旧字段不会重新触发；需要处理缓存读取 |
| DLL 直接 `Label("Some text")`，没有翻译键 | 不在目录中时找不到 | 不触发 | DLL 分析或显示入口采集 |
| 译文文件已写了英文、韩文等错误内容，但项目存在且非占位 | 可能被判为“已有译文” | 可能不会触发缺键 | 仍需要现有原文、语种和译文检查 |

“官方认为缺译”是一条很有价值的证据，但它检查的是翻译数据是否存在、是否合法，不能保证译文本身正确。

## 5. 推荐的最小接入方式

### 先做一次官方缺译目录检查

在语言数据和 Def 准备完成后，读取官方已经加载的键、原文和字段信息，按官方缺译条件补充现有分析。它解决的是“目前哪些条目缺译”，不依赖用户先打开对应窗口。

遇到现有 SQLite 已有同一条目和同一原文时，补观察信息即可，不要再生成一份候选。如果数据库和文件已有有效译文，而游戏当前仍查不到，应记成“译文尚未应用到游戏”的问题，不要再次花 Token 翻译。

### 再记录实际查键失败

可以在 `LoadedLanguage.TryGetTextFromKey` 返回失败时记录，但只处理当前实际游戏语言，排除默认语言的回退读取，并做重入保护。另一种做法是在 `Translator.Translate` 失败分支内记录；这更接近正常翻译用途，但需要处理两个重载和直接调用 `TryTranslate` 的情况。

建议记录：键、默认语言模板、目标语言、原文哈希、英文来源文件；首次出现时再补调用位置。钩子里只入队，文件和数据库工作延后批量处理，不能每画一帧就写库或反复取完整调用栈。

采集目标语言必须明确记录。若 ATC 手动选择的目标语言与游戏当前语言不同，不能用游戏当前语言的缺键结果直接判定另一个语种也缺译。

### 去重继续使用条目标识和原文模板

- Keyed 按所属 Mod、键、目标语言和原文哈希合并。
- Def 按所属 Mod、Def 类型、Def 名称和字段路径对应已有条目。
- 保存填参数之前的模板，不能把 `Stored 1 items`、`Stored 2 items` 当成两份待译原文。
- 原文按默认语言数据取得，保留标点和占位符；不从带重音的结果尝试反向还原。
- 现有短文本逐位置翻译、长文本按语种门槛复用的规则继续生效，不因这次采集改成全局同文替换。
- 核心、DLC、Harmony 等不作为翻译目标的规则继续保留。

这些是接入建议，当前没有提前实施。

## 6. 与这次 ASF / ASGS 截图的关系

两组截图里的设置文案已经能对应到 XML Keyed 原文。另一路静态核对发现，简体译文已经存在于数据库和本地 XML；Mod 却在初始化时把先前的伪翻译结果保存成静态字符串，之后界面继续读旧值。

因此：

- 新增“缺键采集”不会自动刷新这些旧字符串。
- 目录检查能帮助区分“没有译文”和“译文有了但没有用上”。
- 热重载这类文案，需要在已经证明来自某个 Keyed 键的显示读取处重新取当前译文，或找到 Mod 自身的刷新入口。
- 不应把所有只读静态字段重写，也不应重跑整段静态初始化；里面可能有其他业务操作。

当前显示注入器主要追踪字符串常量到显示函数，不会自动追踪“翻译键 → 静态字段 → 另一处显示”的链。这是显示更新能力的缺口，不是缺少一轮 AI 翻译。

## 7. 建议的实施范围与边界

最有价值的方向是增加“官方缺译判断”作为现有 XML/DLL 分析的补充：**目录负责补全已声明的本地化条目，实际查键负责补使用证据，现有 DLL/UI 方案处理没有使用官方本地化接口的文字。**

不需要为了采集强制开启开发者模式，也不需要识别屏幕上的特殊字符。1.6 和 1.7 的核心流程可以共用，各版只保留必要的接口兼容处理。

这份报告只确认接口和静态调用关系，尚不能承诺运行时覆盖率、启动时序和开销。当前没有安装新钩子，也没有改变游戏或用户配置。
