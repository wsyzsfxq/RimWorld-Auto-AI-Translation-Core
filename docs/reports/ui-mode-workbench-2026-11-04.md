# UI 拦截模式下的工作台显示与处理范围

- 日期：2026-11-04
- 状态：源码已修改，仅静态审阅，未编译、测试或运行验证。
- 依据：用户当日确认的三张界面截图及操作要求；取代此前允许 UI 模式显式执行 DLL 工作流的安排，已在当前设计原处及索引更新。

## 修改内容

| 用户要求 | 当前源码处理 |
|---|---|
| UI 拦截模式下不能点击 DLL 分析 | DLL 控件置灰，提示该模式不适用；不改写用户原来的 DLL 分析开关选择 |
| DLL 状态只写一遍 | 在“本地分析结果”的 DLL 行显示“UI 拦截模式不适用”；后两列只画 XML 行，DLL 行留空 |
| 两个控件风格一致 | “强制分析”和“DLL 分析”均使用相同小边框、列表中相同的绿勾和红叉；不可操作时使用灰色 |
| UI 模式仍能翻译 XML | 分析、复核、翻译、试跑继续选择 XML；DLL 候选不进入这些步骤的本次统计和分页 |
| 切回 DLL 模式恢复 | 原有开关偏好、DLL 分析、候选和译文不因切换模式被清空或改写 |

## 后台范围

`WorkflowRuntimeSettings.DllWorkflowApplicable` 表示当前模式是否允许 DLL 工作流，与持久化的 `EnableDllAnalysis` 偏好分开。

- 分析按钮及一键翻译通过分析服务读取该模式；UI 模式只运行 XML 分析。直接 DLL 分析入口也会拒绝操作并说明原因。
- AI 复核、AI 翻译和试跑的候选计数与分页都使用相同的排除范围。现有“本次某个 Mod 的 XML/DLL 分析失败”排除条件继续保留，模式排除不被记录为分析失败。
- 仅完成过 DLL 分析的 Mod，在 UI 模式下不会被当成已经有可用 XML 分析。
- 编辑器按指定条目发起 AI 翻译时，也在修改手工分类之前排除 DLL 条目，避免绕过工作台范围。
- 工作台“需翻译、待判定、未翻译、失败”筛选在 UI 模式下只看 XML，不会因为隐藏的 DLL 旧状态把 Mod 筛进来。
- 模式适用范围在每个 AI 步骤开始时读取；已发出的请求不由本次界面修改强行取消，现有请求取消规则保持原样。

本次只改变这些入口的处理范围和显示。已有结果清理、手工编辑和历史详情的读取仍遵循原有显式操作流程，没有将旧 UI 拦截缓存导入数据库。

## 2026-11-04 后续：开关样式与文字位置

用户后续截图显示，工作台的“强制分析”文字换行并贴近上沿，常用设置里的快捷按钮和名称翻译开关又各用一种样式。此次修改统一为小边框、绿勾／红叉和单行文字：

- 四处共同使用 `WorkflowUiStyle.ToggleButton`；“显示翻译快捷按钮”使用短名称，完整用途放在悬浮提示中。“翻译 Mod 名称”原有的模型配置限制、取消和保存逻辑保留。
- 工作台不再把两个开关硬塞进七分之一宽度的一列；以同一绘制样式测量实际文字，再加图标和边距计算宽度。选项行从 27 改为 34，使正文和图标具有完整的单行高度。
- 公共按钮文字使用局部样式副本，明确关闭换行、清除继承的内边距及偏移并垂直居中；绘制后还原字体、对齐和换行状态，不修改游戏的共享样式。
- 静态读取本机 1.7 的 `Widgets.Label → GUI.Label → GUIStyle.DrawTextIn` 确认对齐和换行均会传入后端。原问题有可见的空间不足和换行路径；本次没有靠任意移动文字几像素修补。

这一轮仅修改源码并作静态阅读，没有重新编译、部署、启动游戏或执行界面验证。实际位置和字形待后续交付后由用户查看。
